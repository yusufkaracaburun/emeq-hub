    **Stap 2 — Schrijf ADR `.docs/decisions/account-subscriptions.md`** met secties:
    - **Status:** Accepted YYYY-MM-DD
    - **Context:** Use-case B vereist multi-tenant subscription-state per Account+Connection; Cashier-Mollie (Phase 6) is single-tenant en daarom niet bruikbaar.
    - **Decision:** Eigen `AccountSubscription`-model + state-machine + dispatcher-pattern in MollieWebhookController (D-15). Geen herbruik van Cashier `Plan`-model (D-06). Geen state-history-tabel in v0.2 (D-22).
    - **§ Scope-niveau van Account-Subscription-mutate-endpoints (MEDIUM #3):**
      - **Decision:** Mutate-endpoints (`POST .../{id}/pause`, `POST .../{id}/resume`, `DELETE .../{id}`) hanteren **per-Consumer scope**, niet per-Account.
      - **Implicaties:** Een Consumer met meerdere Accounts (bv. een SaaS die meerdere scholen beheert) kan via één PAT subscriptions over al zijn Accounts heen muteren. Mutate op een sub die bij een vreemde Consumer hoort → 404 (D-12). Mutate op een sub die bij Account-B hoort terwijl de PAT primair bij Account-A van dezelfde Consumer "lijkt" → 200 (allowed).
      - **Bewijs:** Plan 07-06 test `pause_on_subscription_of_other_account_same_consumer_returns_200` pin't dit gedrag. Test `cross_consumer_pause_returns_404` pin't de tegenovergestelde isolatie.
      - **Rationale (waarom B i.p.v. A — strikter per-Account):** Sanctum PAT-scope is per-Consumer (PersonalAccessToken → Consumer-tokenable, niet Account). Een per-Account scope-niveau zou ofwel ofwel een extra account-id-param vereisen in elke mutate-call (UX-regressie), ofwel een aparte PAT-laag per Account (Sanctum-misbruik). Per-Consumer scope is consistent met de `findOwnedConnection`-helper van Phase 3 (`ConnectionController` regels 97-124).
      - **Reviewer-instructie:** Een Consumer is in scope's contract verantwoordelijk voor het routeren van mutate-calls naar het juiste Account-context-id (bv. via hun eigen "active school"-state). De Hub verifieert alleen Consumer-ownership, niet Account-context.
    - **§ Integration-test-keuze (MEDIUM #4):**
      - Pad A (token-aanwezig): integration-test draaide live op YYYY-MM-DD; bewijs in `07-08-ACCEPTANCE.md` item #11.
      - Pad B (token-afwezig): integration-test ⏭️-skipped tot v0.2.1. SC-4 vendor-coverage uitgesteld. Triggers voor re-run: (1) Connect-test-token verkregen, (2) v0.2.1-release-window opens, (3) handmatige UAT bij Naschool-go-live.
    - **Consequences:**
      - + Multi-tenant subscription-state-machine over verschillende Mollie-accounts heen mogelijk
      - + Coëxistentie met Phase 5a pass-through (D-30) — Consumers kunnen kiezen tussen raw pass-through of higher-level wrap
      - + WebhookPayloadRouter ook bruikbaar voor toekomstige Snelstart-event-routing (Phase 5c kan op dit pattern leunen)
      - − Tweede subscription-laag naast Cashier vereist mental-model-discipline; ADR is de single-source-of-truth voor "wanneer Cashier vs AccountSubscription"
      - − State-history is log-only; Phase 9 admin moet logs aggregeren als history-view wenselijk wordt
      - − Per-Consumer scope op mutate-endpoints betekent dat Consumers met meerdere Accounts hun eigen client-side Account-context moeten managen
    - **Alternatives considered (rejected):**
      - Cashier-Mollie fork voor multi-tenancy — afgewezen wegens upstream-maintenance-kosten
      - Spatie/laravel-model-states package — afgewezen wegens dependency-minimalisme (Phase 6 stance gehandhaafd)
